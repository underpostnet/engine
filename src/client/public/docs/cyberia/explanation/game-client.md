# Cyberia game client

**Path:** `cyberia-client/` · **Language:** C11/GNU11 → WebAssembly (Emscripten) · **Role:** presentation runtime for Cyberia

`cyberia-client` is the rendering and interactive runtime for the Cyberia MMO extension on Underpost Platform. It captures input, predicts the local player, reconciles against authoritative snapshots, interpolates remote entities, and renders the world. It owns the render policy locally.

It is **not** a world-simulation authority. The authoritative simulation runs on `cyberia-server`. Persistent content and asset metadata come from `engine-cyberia` via REST.

---

## Operating model

Three independent processes, non-overlapping roles. The ecosystem is playable only when all three are running and healthy at the same time.

```text
engine-cyberia          cyberia-server          cyberia-client
content authority       simulation authority    presentation runtime
  ^ REST                  | WebSocket binary
  | atlases, asset        | snapshots  (server -> client)
  | metadata, optional    | input cmds (client -> server)
  | client hints          v
  `---------------- Browser tab: prediction, reconciliation, interpolation, render
```

- Each service owns its own monitor and reconnector.
- The client reconnects to `cyberia-server` over WebSocket and fetches content from `engine-cyberia` over REST.
- If any of the three services is unhealthy, the game moves to standby until all three recover.

The client speaks two transports:

- **WebSocket** to `cyberia-server` for snapshots and client events (JSON messages in binary frames)
- **REST** to `engine-cyberia` for atlas frames, asset blobs, and optional client-hints overrides

Asset distribution flows through Underpost Platform's static and PWA pipeline.

---

## Render loop

The render loop runs at vsync. Tick simulation is decoupled from render frames via a fixed-timestep accumulator. Step ordering inside one render frame:

1. **Reconciliation** — replace the own state with the newest snapshot; drop the client events up to `inputConsumedThrough`; replay the rest from the snapshot `frame` to the current frame.
2. **Input capture** — drain raw OS events.
3. **Input dispatch** — UI hit-test → push client events (`kind`, `frame`, `sequence`, payload).
4. **Fixed-timestep prediction** — while accumulator ≥ `tickDuration`, advance one frame; then send the new events once.
5. **View** — draw the own player between the last two fixed steps; interpolate remote entities.
6. **Render** — read view models; never mutate world state.

Render frame rate is independent of simulation tick rate. The fixed-timestep accumulator ensures the predicted simulation advances at the authoritative `tickRate` regardless of FPS.

## Presentation ownership

The client owns its render policy. The authoritative server holds no presentation state.

Three layers, strictly inward-dependent:

1. **`content/presentation_runtime.{c,h}`** — sole owner of every presentation value. Fires a single asynchronous GET against `/api/v1/cyberia-client-hints/:CYBERIA_CLIENT_HINTS_CODE` at startup, polled once per render frame. When the response settles, parses palette, entity colour keys, status-icon visuals, and camera/cell tunings into a process-local table and writes a one-shot hydration into `g_game_state` (cell_size, interpolation_ms, camera.zoom). The C client carries NO compile-time palette or status table — only a tiny inline neutral-grey bootstrap so the splash screen has something to draw while the fetch is in flight. The canonical schema for the response lives at engine-cyberia's `src/client/components/cyberia/SharedDefaultsCyberia.js`.
2. **Renderers** — call `presentation_runtime_palette("KEY")`, `presentation_runtime_status_icon(u8)`, `presentation_runtime_status_border(u8)`, `presentation_runtime_entity_fallback_color(entity_type)` at each use site.

What lives in this layer:

- Named palette (colors).
- Per-entity-type fallback color keys.
- Status-icon visual table (icon stem + border color per numeric ID).
- Camera smoothing / zoom defaults.
- Interpolation window.
- Dev-overlay flag.
- Viewport screen factors.

What does **not** travel on the WebSocket init or AOI streams:

- Palette.
- Camera knobs.
- Dev-overlay flag.
- Interpolation window.
- Status-icon visuals.
- Per-entity-type color keys.

The numeric status-icon u8 still rides on the AOI wire — that is the protocol-level half. The icon stem and border color are presentation and are resolved entirely on the client.

### Optional client hints

`GET /api/v1/cyberia-client-hints/:instanceCode` (engine-cyberia REST, **not** cyberia-server) returns a JSON document mirroring the structure of the compile-time defaults. The client is required to function with no successful call to this endpoint:

- 200 with `{ palette, entityColorKeys, statusIcons, cameraSmoothing, cameraZoom, defaultWidthScreenFactor, defaultHeightScreenFactor, interpolationMs, devUi }` — overrides applied on top of defaults.
- 404 if the instance has no overrides — defaults are used.
- Network error — defaults are used.

No authentication; presentation hints are not secret. The Go authoritative server never calls this endpoint.

## Tick-aware components

### Session

`sim/replication.{c,h}` keeps two per-connection counters:

- `session_frame()` — completed fixed steps in this session. `session_frame_advance()` is its only writer, once per fixed step.
- `session_next_input_sequence()` — monotonic sequence for outgoing client events. Never reused.

### Prediction

Prediction moves the own player only. Every other entity takes the server state. The live step and the replay use one motion function, `self_motion_step()`.

- `prediction_on_snapshot(state, frame, consumed)` — the decoder hands over the self block. A newer state replaces one the reconcile did not apply yet.
- `prediction_reconcile()` — phase 1 of the tick: replace the own state with the newest server state, drop the client events up to `consumed`, and replay the rest from `frame` to the current frame.
- `prediction_step(s)` — one fixed step; `s` is the frame the step completes.
- `prediction_prev()`, `prediction_self()` — the last two fixed steps. The view draws the own player between them. View-only; it never writes simulation state.

### Interpolation

`interpolation_compute_view()` owns remote-entity render-time positions. It is the only writer of remote `interp_pos` and never touches the local player. It lerps from the previous position to the newest snapshot position over `interpolation_ms`.

### Client event pipeline

```
mouse / touch / keyboard
        │
        ▼
input/                  raw OS events
        │
        ▼
UI hit-test cascade  ──► modal/inventory/HUD consumed?
        │  no
        ▼
client_event_push       stamps frame + sequence + time; keeps the event
        │
        ▼
client_event_flush      after the fixed steps: sends each new event once
```

`net/client_event` is the one uplink. A module pushes an action and touches no stamp, no sequence and no socket. The list keeps each event until a snapshot's `inputConsumedThrough` passes its sequence (`client_event_trim`), so the reconcile can replay it.

### Pointer controls

One pointer, a finger or the mouse, moves the player in two ways: tap or click a point, or drag a floating joystick. The joystick works on every platform and at every viewport size. `input/pointer_gesture.c` sorts each press. `ui/hud_joystick.c` draws the joystick.

| Gesture                   | Result                                                                                                                                                |
| ------------------------- | ----------------------------------------------------------------------------------------------------------------------------------------------------- |
| Tap or click on the world | The player walks to the point. The tap goes out on release, at the press position.                                                                    |
| Quick press on the world  | Released within 150 ms, a press is a tap, however far the pointer moved. A fast click on the move never starts the joystick.                          |
| Held drag on the world    | Held 150 ms and moved past 35 px, a press shows a joystick at the press position. The pointer sets one of eight headings, the same as the arrow keys. |
| Thumb in the inner 15 %   | No heading. The player stops.                                                                                                                         |
| Release after a drag      | The joystick hides and the player stops. The drag sends no tap.                                                                                       |
| Second finger             | Pinch zoom. It cancels a pending tap and stops the joystick.                                                                                          |
| Finger on the UI          | The UI owns the touch. The tap goes out after a 120 ms pinch window. A drag never starts the joystick.                                                |
| Click on the UI           | The UI owns the click. The tap goes out on the press. A drag never starts the joystick.                                                               |

The joystick adds no wire message. It sends the same synthetic steering taps as the keyboard: the same reach, the same refresh at the action cooldown, the same stop. While it steers, the arrow keys wait. The base stays where the drag started.

To check a change, use a phone or a browser with touch emulation, and a desktop browser. A pinch needs a real device.

1. Tap the ground. The player walks there. No joystick shows.
2. Hold one finger still for a second, then lift it. The player walks to that point.
3. Drag from any point of the ground. The joystick shows under the first contact. The player walks in the drag direction, in eight headings.
4. Move the thumb back to the base. The player stops. Lift the finger. The joystick hides.
5. Drag, then put a second finger down and pinch. The camera zooms, the player stops, and no tap moves the player.
6. Drag the Quest Journal list and the inventory bar. They scroll. No joystick shows.
7. Open the Instance Map. Drag and pinch it. No joystick shows.
8. On a desktop, click the ground: the player walks there on release. Drag the mouse on the ground: the joystick shows and steers. Release: the player stops.
9. On a desktop, click toolbar buttons and drag the inventory bar. They respond on the press, as before. Steer with WASD and zoom with the wheel.

## Wire format

Every message in both directions is a JSON envelope `{ "type": ..., "payload": ... }` sent in a binary WebSocket frame. `net/message.c` dispatches on `type`.

The server sends one `snapshot` per tick. Its payload carries:

| Field                  | Meaning                                                                   |
| ---------------------- | ------------------------------------------------------------------------- |
| `frame`                | the client frame this state stands for; 0 before the first consumed event |
| `inputConsumedThrough` | highest client event sequence a tick has applied for this client          |
| `entities`             | the AOI entities, life rounded up to whole numbers                        |
| `self`                 | the own player block                                                      |

The decoder hands the self block, `frame` and `inputConsumedThrough` to `prediction_on_snapshot()`. `prediction_reconcile()` applies it at the start of the next tick.

The other server messages — `init_data`, `session_end`, `resume`, `metadata`, `combat_text`, `audio_event`, `drop_spawn`, `drop_collect`, `chat`, `chat_ack`, `party_ack`, `friends`, `friend_ack`, `dialog_ack`, `shop_ack` — are not part of the per-tick replication stream.

The first message of every connection is `auth`: `{ticket}` with the launch ticket the page took from its address fragment, `{}` without one. A refusal shows the session card, whose ways open the launch bridge of the portal: **Continue as guest** or **Sign in** ([accounts and persistent players](accounts-and-persistence.md#launch-flow)). An account session keeps the resume ticket of `resume {ticket}` in memory; after a lost connection or a server restart it reconnects with it and comes back without the portal ([resume](accounts-and-persistence.md#resume-after-a-dropped-connection)). A guest card opens a new connection after a lost connection or a restart. The settings button opens the same card as the settings menu: the sound and full-screen toggles, then World select, Play as guest, Sign out, or Sign in to keep progress ([leaving](accounts-and-persistence.md#leaving)).

The client sends one `events` message per frame with new events. Its payload is `{ "events": [ ... ] }`; each event is an envelope whose payload carries `seq`, `frame` and `timestamp`.

## REST fetches (engine-cyberia)

The client speaks REST directly to engine-cyberia for content. None of these calls go through cyberia-server.

The client draws a render by the cid of its definition, never by a label. A label stands for the cid
of the definition the world binds it to: the `metadata` message sends that definition. A held stack
keeps the cid it was granted with. Renders are cached by cid, so two labels of one definition share
one download. The engine reads a definition from its cache, else from the Object Layer authority, so
a definition no served release holds keeps its render. The primary render is the bytes the
canonical render CID addresses, at one pixel per cell, and the layout describes that same render.
The engine also keeps an upscaled derived render for viewing; the client never downloads it.
The [render contract](../../object-layer/explanation/render-contract.md) defines these terms.

| Endpoint                                                         | Purpose                                       |
| ---------------------------------------------------------------- | --------------------------------------------- |
| `GET /api/v1/atlas-sprite-sheet/layout/:cid`                     | Frame layout JSON of a definition's render    |
| `GET /api/v1/atlas-sprite-sheet/render/:cid`                     | Primary render PNG, one pixel per cell        |
| `GET /api/v1/cyberia-dialogue/code/default-:itemId`              | Dialogue lines for an NPC                     |
| `GET /assets/ui-icons/:iconId.png`                               | Status-bar icons                              |
| `GET /api/v1/cyberia-client-hints/:instanceCode`                 | Optional presentation overrides               |
| `GET /api/v1/cyberia-instance/instance-map/:instanceCode/static` | Instance Map graph (nodes, edges, POIs)       |
| `GET /api/v1/cyberia-universe/instance/:instanceCode`            | The universe of this world, with availability |

All requests are CORS-simple GETs (no preflight) and cacheable. None require credentials.

## Instance Map

The Instance Map has two views. **WORLD** shows the maps of this instance and their portal links.
The engine places the maps in `src/projects/cyberia/instance/instance-map-layout.js`, the geometry of the [world preview](universe.md#world-pictures).
The static payload gives each node its centre (`position`) and size (`w`, `h`), in layout units: the longest map side of the world is 1.
The client requires `position`; deploy the engine update before the client update.
Every map uses the same scale and keeps its grid proportions.

Maps on neighbour layout cells touch, whatever their sizes. A run of empty cells stays as one gap.
A map with a [world origin](map-registry.md#ownership) keeps its physical place.
The client gives each map its bounds once per static payload. Edges closer than 1/100 of a map cell take one value, so maps that touch meet on one pixel at every zoom.
Two maps join when they share an edge of positive length. A corner or an overlap does not join.
Maps that join form one surface: one rim goes around it, and a shared edge has no gap or border.
A portal link across a shared edge shows only while one of its maps is selected. A link between maps apart always shows.
Each map keeps its own click area. The right and bottom edges belong to the next map when maps meet.
The own map, the selected map and the hovered map take their marks inside their bounds, so a mark never opens a gap.
The view opens with the whole world as large as the frame allows, until one map cell spans 8 px.

A name plate sits at the centre of each map and each world card. It is blue, so it stands out from the markers, and gold on the selected node.
Its text size follows the card, from 10 to 20 px. A long name takes a smaller text first, then ends with an ellipsis.
Maps with the same name include their codes. A plate hides when the card is too small to hold it.
Matching preview images fill their map bounds. Images with different proportions stay centred within the map.

**UNIVERSE** shows the worlds of its [universe](universe.md) on their cells, the routes between them, and what serves each world now. A world card has the proportions of its world preview (`w`, `h` of the view). Both views are for navigation and planning; neither reproduces the gameplay viewport.

One integrated widget with two modes, split across two modules:

- **Toolbar** (`ui/toolbar`) — the top HUD strip: the compact map readout left-aligned, and the right-hand toggle row `[chat][social][quest][map][settings]`. The quest button shows/hides the Quest Journal and the map button shows/hides the minimap; both are hidden by default and stay open together. A tap on either closes the chat and the social panel. The coordinate readout opens the expanded Instance Map, which morphs to the full screen with an eased transition and retracts the same way on close.
- **Side stack** (`ui/hud_side_stack`) — the right-hand column the HUD panels live in, between the toolbar and the inventory bar: the minimap on top and the Quest Journal beneath. The chat or the [social panel](social.md#social-panel) takes the whole column while it shows, over the minimap and the journal, and the social panel covers the chat. The column sizes to the room the bar leaves. When the journal is open the minimap gives way to at most half of the column, and the journal takes only what its content needs; a map slot under 100 px gives way. Each panel keeps its own state across toggles for the session: the journal its scroll, sections and pages, the minimap its zoom and its texture toggle.
- **Minimap** (`ui/hud_minimap_overlay`) — the current map only: its map preview at 55 % over a see-through backdrop, with its border, fitted to the slot at zoom 1, and following the player at a closer zoom up to the map edges. Over it, in this order: the authored presence as hollow squares, the live players, bots and resources as filled squares, each portal as a gate where it stands, and the own player with its facing. An exit to another map has an arrow toward that map and a tag with its name; a link inside the map has a ring. A tag takes the first side of its gate that is clear of the controls, the markers and the other tags, and the pointer over a gate names its exit in full. The controls stand in the top right corner of the map: the texture toggle above zoom in and zoom out, in a row when the map is short. With the texture off, a grid on a see-through fill marks the map and every marker stays. The world shows through the map in both modes; the header, the controls and the markers stay opaque. No other map is drawn.
- **Container** (`ui/modal_map`) — compact mode is the always-on readout (map code, position, fps) hosted inside the toolbar; expanded mode is the full-screen morph target.
- **Content** (`ui/modal_instance_map`) — renders the Instance Map inside the container: a non-blocking translucent full-screen panel (the world keeps rendering behind it).

Strict independence from the gameplay renderer:

| Concern    | Owner                                                                                                                                                    |
| ---------- | -------------------------------------------------------------------------------------------------------------------------------------------------------- |
| Graph data | `data/instance_map_data` and `data/universe_map_data` — engine-cyberia REST only, never the AOI stream                                                   |
| Camera     | own pan/zoom with smooth exponential interpolation (drag pan, wheel zoom, pinch zoom)                                                                    |
| Layout     | WORLD: the map geometry of the engine; UNIVERSE: the world cards packed on their cells; a view never turns the authored arrangement                      |
| Selection  | tap a node → contextual panel: a map's providers and portals, or a world's thumbnail, status, route and TRAVEL; the camera moves a node its panel covers |

Data lifecycle:

1. Opening the overlay fetches the **static** payload once: graph nodes with their cells, portal edges, and authored `presencePois` carrying map-cell presence status, their quests with `prerequisiteCodes`, and their actions with the quests that use them. The instance code arrives in the simulation server's `metadata` message.
2. The client marks a quest POI active while its quest is acceptable or active in the local quest store, and an action POI active when it stands alone or one of its quests is. It marks them again at each quest store change; no request names the player.
3. The UNIVERSE view reads `/cyberia-universe/instance/:instanceCode` the first time it shows, and again every 20 seconds while open, past the response cache (`fetch_forget`). It loads a world picture only when its card is drawn.
4. Closing the overlay discards a late response.

The UNIVERSE view draws each world with its world preview ([world pictures](universe.md#world-pictures)), on a card of the proportions of that preview, and a dotted tile with its initials while the picture loads or when it has none. It outlines this world in green, marks each world with its status (ONLINE, CLOSING, OFFLINE), and each route with travelling pulses; a one-way route ends in an arrow. A selected world shows the thumbnail its author set (none when there is no thumbnail: the card already shows the preview), its name, its status and whether a route leads there; it never shows a server address. A world the served release lacks shows dimmed. A selected world offers **TRAVEL** only when a route leads there from this world and a server of it takes new sessions; otherwise the button names the reason (NO ROUTE FROM HERE, WORLD OFFLINE, WORLD CLOSING, NOT IN THIS RELEASE). TRAVEL closes the overlay and leaves through the session gate, which names each step: the final save of this world, then the entry of the target. An account whose target runs the server build it plays on enters the target in the page; otherwise, or when that fails, the launch bridge of that world opens with the same principal ([travel in the page](accounts-and-persistence.md#travel-in-the-page)). A route never proves that a server is up; a world stays on the graph while it is offline.

Live player position never travels through this API — engine-cyberia holds no simulation state. The overlay marks the player's node (and cell fraction within it) from the client's own predicted position, refreshed every frame.

At normal zoom, POIs render only their authored presence-status icon, sized with the card. Once a map cell spans 9 px on screen, static action and quest capability icons appear; quest activity only changes capability emphasis. The local player's live presence and authoritative stats sum remain client-side. Decorative map content without a presence status is not rendered as a POI.

- The inventory bar shows every cell the capacity rule can open: stacks, open slots, then locked
  slots with the `lock` icon and their level ([inventory capacity](inventory-capacity.md#locked-slots)).
  Each cell is a bag slot; a tap opens a stack and a drag moves it ([moving stacks](inventory-capacity.md#moving-stacks)).
  The item card equips and unequips the stack it shows.
- The toolbar row reads `[chat][social][quest][map][settings]`; settings (the `engine` icon) is the
  rightmost button. It opens the settings card: CYBERIA PORTAL leaves for the portal, SOUND ON or
  OFF and FULL SCREEN ON or OFF act at once, then the other ways out of the session. The chat button carries the unread count of every
  conversation and opens the HUD chat. The social button (`friends` icon) carries the friend

- A pending party invite never blocks play: the own bubble counts invites and the inviter's bubble
  carries the party mark ([chat and parties](social.md#parties)).
- The shop and the assembler show "Bag full" on a card whose result has no free slot.

To check a change, use a desktop browser and a phone (or touch emulation):

1. Tap the own bubble. The own profile opens on Profile, with Storage and Stats. No dialogue opens.
2. Open Storage. Drag a stack from the bar into an open cell and back. A locked cell turns the drop
   back and, on a tap, names its level.
3. Tap a locked bag slot. A toast names the level that opens it.
4. With two clients, open the other player's profile and invite it. Accept from the Party tab of the
   other client's social panel. Both Party tabs list two members.
5. Open the HUD chat. Send on World and on Party; type WASD into the input: the player does not move.
6. Close the other client. The party ends on the first client.
7. On an account world, add the other player as a friend and accept. Both nameplates show a heart;
   a direct line with `:smile:` shows the icon in the chat and in the bubble preview.
8. Open the world in a second tab. The first tab shows the session card with PLAY HERE.

## Stats and progression

Every living entity's overhead HUD shows `[stats] lv.<level>` and `[stack] <stats sum>` above its nameplate, and a gold XP bar under its HP bar. The local player's bar fills with its progress through the current level and carries an `XP n / m` label in a smaller font; entities whose XP the client cannot read show an empty, unlabeled bar.

A destructible obstacle shows only the HP bar, filled from the `life` and `maxLife` of its snapshot, and only while it stands. An ordinary obstacle sends `maxLife` 0 and shows none. A depleted obstacle draws its dead items, or nothing when it has none.

The Stats tab of the interact modal draws one shared stat panel per block: the stats icon, the signed sum, and a two-column grid with one icon per stat. Every entity gets its effective stats. The local player also gets the OL modifiers, base stats, and temporary modifiers from the self snapshot. The inventory modal draws the same panel for one item.

An XP award floats as gold `+N XP` combat text over the earner only. A server level increment triggers a `LEVEL UP` aura: shaded gold sparks stream from the entity's feet up past its head for 3 s under a spinning star and a label, and the whole effect follows the entity as it moves, for any entity in view. First sight, repeated snapshots, and lower levels do not trigger it.

An `item_consume` event whose `behavior` is `consume-on-pickup-heal` triggers the heal aura on the consumer: shaded green sparks turn on a ring around its feet while more sparks and pixel plus marks rise through its body for 1.8 s, following the entity. It plays for a world loot pickup and for a held unit the zero-waste heal consumes alike, for any entity in view. Any other behavior triggers nothing.

A player standing on a portal shows a blue transport bar at the top of its overhead stack, with `Transporting...` centered inside. The teleport charge fills it. While the charge runs, shaded blue sparks circle the player's feet and climb a spiral through its body; the charge raises the column and adds sparks, so the aura gathers as the jump nears. The snapshot carries `onPortal` and `portalHoldProgress` for every player, so every viewer sees both on every player in view.

Every damage `combat_text` throws a hit burst at its point: a few shaded red sparks jump up, fall back and shrink away in under half a second. It marks each hit, a projectile on any entity in view above all, without hiding the fight.

A defeat of a player or bot triggers the death cue: shaded red sparks burst out of the body and fall while a `skull` icon rises over it for 2.6 s, following the body. It fires once, when an entity seen alive in the prior snapshot is dead in this one. An entity first seen dead, or still dead, triggers nothing. A resource is extracted, not slain: it goes straight to its extracted state with no cue.

While either cue runs, the entity's whole overhead stack, presence icon included, yields the space to it and returns when the cue ends.

The cues are visual only. Their sounds arrive as `audio_event` messages the server broadcasts to every player whose area of interest covers the event, so a defeat, an extraction, or a level gained sounds the same for everyone in reach. The client plays the id through the map's audio bindings.

Item slots badge an object layer with the `stack` icon and its signed stat sum, red when negative.

An inventory slot whose item triggers skills shows, above the slot, the entity each skill summons. The init_data skill map names the entity (`summonedEntityItemId`; `$active_skin` is the player's active skin), and each `metadata` delta replaces the skills of the definitions it carries, and the preview draws it as the stack the server spawns, through the same stack icon renderer as the rest of the UI. The slot keeps the trigger item's own icon. Distinct entities share one row, up to three. Each preview carries the quantity badge of the units the player holds of its entity; a slot that summons its own item counts the units of that stack alone. A tap skill shows only over an active slot. A held skill (`held` in the skill map) runs by itself on every held stack, so it shows over an inactive slot too.

One bar under the row shows the cooldown of the row. For a tap skill it is the shared action cooldown from `self.actionReadyInMs`: it fills while the cooldown runs and turns green when the next tap fires skills. A green bar does not promise a summon: the server still rolls each skill's chance. For a held skill it is the consume cooldown from `self.consumeReadyInMs`. The row takes no input and hides while the player is in stasis.

A consumable has no Use button. Its held skill, `zero-waste-auto-consume-heal`, consumes one unit by itself once the missing life takes the whole heal. Over a consumable slot the preview shows the item itself with the units left in that stack. The server spends one stack at a time, in slot order, so the counts drop on one stack, then on the next. The inventory modal follows its stack by slot, then by item id, so it closes when the last unit is consumed.

The server sends six values in canonical order. The client displays these values and uses the supplied movement speed.

## Build and run

```bash
cd cyberia-client

# Development build (BUILD_MODE=DEBUG)
make -f Web.mk clean && make -f Web.mk all

# Release build
make -f Web.mk clean && make -f Web.mk all BUILD_MODE=RELEASE

# Serve it against a local engine and game server
CYBERIA_WS_ORIGIN=ws://localhost:8083 python3 wasm-driver.py --port=8082 --directory=bin \
  --data-server-url=http://localhost:4008
```

`BUILD_MODE` picks debug or release code only. No server URL is a build argument — see
[Compile-time configuration](#compile-time-configuration).

The build is part of the Underpost Platform static + PWA pipeline; production deploys go through `underpost client` and `underpost deploy`.

## Compile-time configuration

### Server URLs

No server URL is compiled in. The websocket origin has one source:
`CYBERIA_WS_ORIGIN`, which `wasm-driver.py` injects as `window.CYBERIA_WS_ORIGIN`.
The client dials `<origin>/ws` for the default world and `<origin>/<instance>/ws`
for any other. `instance-build-manifest` writes the value of each environment to
the instance env ([origins](accounts-and-persistence.md#origins)).

The Data Server URL is a command line argument, not a build argument:

```
wasm-driver.py --data-server-url=<origin>
  -> window.CYBERIA_ARGV -> Module.arguments -> main(argc, argv)
```

`config_init()` reads `--data-server-url=<origin>` from `argv`. Both values are
required: `wasm-driver.py` refuses to start without them, and the client stops
with a log line if one is absent. There is no fallback, no config file and no
runtime override.

`wasm-driver.py` appends any other flag to the client argv. `fetch_init()` reads
two stream diagnostics:

| Flag                                  | Effect                                                                               |
| ------------------------------------- | ------------------------------------------------------------------------------------ |
| `--stream-disable=<mode>[,<mode>...]` | Turns off `audio`, `audio-network`, `audio-runtime`, `atlas` or `dynamic` streaming. |
| `--stream-profile`                    | Records stream events in `Module.streamTrace` (30,000-entry ring, read in DevTools). |
